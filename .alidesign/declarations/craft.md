# Craft declaration

## Product-specific quality intent

- Feel editorial, direct, technical, and personally specific to Cooper Oak.
- Let proof and native GitHub behavior carry trust; the custom visual carries
  identity, not application chrome.
- Preserve some sharp operational clarity from the original reference without
  copying its dashboard structure, fake controls, or generic SaaS voice.

## Content truth and prohibited fabrication

- Claims must map to `content-evidence.md` and a public proof link.
- Do not publish volatile counts, invented adoption, placeholder contact
  links, completion claims for draft content, or an implied six-project system.
- `Started from scratch in 2026` and `Goal: 100 projects` remain explicitly
  authored narrative, never verified telemetry.
- No `TODO`, `TBD`, `Add your...`, fake status, or empty evidence link.

## Information density and hierarchy

- One shallow signature strip, one H1, one primary link, three selected
  projects, three principles, and one repository exit.
- Single-column reading at every width. No card grid, table, nav bar, badge
  wall, module registry, nested panel, or repeated project inventory.
- Each project gets one outcome sentence and one proof sentence. More detail
  belongs in the repository.
- Native GitHub Pins and contributions are respected as the next layer of proof.

## Typography, imagery, material, and visual-expression expectations

- Native Markdown owns all essential identity, copy, headings, and links.
- Signature typography is large, sans-serif, and sparse. No source text below
  20px desktop or 26px mobile; no micro uppercase eyebrow or dense metadata.
- English is primary; Chinese contributes one short voice line only.
- Use the avatar's exact `#6ed959` green and pixel-cut geometry with neutral
  black, off-white, and gray. Do not reintroduce the blue console accent.
- Flat editorial composition: no gradients, glass, drop shadows, fake depth,
  rounded card shell, app logo tile, or decorative control affordance.
- The signature strip may duplicate the name visually, but native text remains
  the accessibility and information source.

## Interaction and motion intent

- All apparent actions are real `<a>` links rendered by GitHub or the semantic
  preview. Static SVG contains no button, focus, selected, hover, toggle, or
  cursor language.
- No animation. Motion has no task value on a static Profile README.
- Browser/GitHub navigation supplies return and focus behavior.

## Accessibility and responsive baseline

- Text contrast target: at least 4.5:1 for normal-sized copy; green is not used
  as small text on the light canvas.
- All identity and links remain readable without images or color.
- Informative image alt text is concise; repeated copy is not stuffed into alt.
- Verify 1440px desktop context, approximately 860px README width, 390px and
  320px narrow contexts, light/dark schemes, natural wrapping, and 200% zoom.
- The mobile signature is a composed variant, not a scaled desktop screenshot.
- Project names may wrap; font size must not shrink to preserve one line.

## Generic-output risks relevant to this product

- Control-plane/dashboard costume on static content.
- Equal rounded cards, nested border shells, oversized generic SaaS mark.
- Tiny monospaced metadata, slash numbering, uppercase labels, and status chips.
- Repeating the same repositories in different modules.
- Generic builder slogans that could survive a username swap.
- Overstating experimental or draft repositories as released products.

## Accepted exceptions

- Four SVG files are allowed for one signature composition: desktop/mobile and
  light/dark. This avoids unreadable shrinkage and theme mismatch; it does not
  authorize four separate layouts or four content systems.
